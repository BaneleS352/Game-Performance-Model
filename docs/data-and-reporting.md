# Data and Reporting Reference

## Source dataset

Each source row represents one game’s daily activity. Required columns are:

| Column | Type | Meaning | Validation / interpretation |
|---|---|---|---|
| `Date` | date | Activity date | Parsed with `pd.to_datetime`; invalid dates are removed. |
| `SystemName` | text | Distribution/system name | Trimmed; required for `Game_ID`. |
| `TournamentName` | text | Game/tournament name | Trimmed; required for `Game_ID`. |
| `Clients` | number | Client activity count | Required, finite, non-negative. |
| `BetCount` | number | Number of bets | Required, finite, non-negative. |
| `Stakes` | number | Stake value, displayed as ZAR in the UI | Required, finite, non-negative. Currency `R` and thousands separators are cleaned. |
| `GGR` | number | Gross gaming revenue | Required and finite; may be negative. |

Optional source fields such as `GGR_Perc` and metadata candidates (`Provider`,
`Supplier`, `Studio`, `GameCategory`, `GameType`, `Category`, `Theme`,
`Volatility`, `RTP`, `Market`, `Country`, `Brand`, `DeviceType`) are retained or
used when available.

## Canonical cleaned data

Produced by `clean_game_daily` and saved as `clean_game_daily.pkl`.

| Field | Definition |
|---|---|
| `Game_ID` | Stable key `SystemName::TournamentName`. |
| `First_Observed_Date` | Minimum valid date for the game. |
| `Days_Since_First_Observed` | One-based lifecycle age: date minus first observed date plus one. |
| `GGR_Perc_Calc` | `GGR / Stakes` when stakes is non-zero; otherwise missing. |
| `attrs` | Audit counts such as input rows, invalid dates, removed rows, duplicates, and output rows. |

Duplicate daily records are resolved by keeping the last valid occurrence for
each `(Date, Game_ID)` pair.

## Lifecycle snapshots and calculated fields

Snapshots are point-in-time rows for one game/checkpoint/horizon. The default
`Settings` configuration creates six checkpoints—21, 28, 35, 42, 49, and 56
observed days—and a seven-day target horizon. Notebook 04 prefers `(14, 7)` if
that pair exists in the trained artifact, otherwise it falls back to the last
available pair and prints a warning; this is a compatibility preference, not a
different default `Settings` value.

### Feature families

- Calendar: launch month/weekday, observation-end month/weekday/day/week.
- Window totals/means/std: `obs_*_sum`, `obs_*_mean`, `obs_*_std`.
- Recency/shape: first, last, median, coefficient of variation, slope,
  first-to-last growth, recent means, recent-to-early ratio, peak, days since
  peak, zero/positive days.
- Commercial ratios: bets per client, stake per client, stake per bet, GGR
  margin, with three-week variants and growth.
- Weekly aggregates: week-one, week-two, and week-three sums and growth where
  the observation window supports them.
- Log transforms: `log_*` features used to stabilise skewed non-negative values.
- Size bands: client bands `(100, 1,000, 10,000)` and stake bands
  `(10,000, 100,000, 1,000,000)`.
- Missing indicators: `missing__<numeric_feature>` for each model numeric field.

### Target fields

Historical snapshots with `require_future=True` contain seven-day future targets:

| Target | Meaning |
|---|---|
| `target_clients` | Future Clients total. |
| `target_betcount` | Future BetCount total. |
| `target_stakes` | Future Stakes total. |
| `target_ggr` | Future GGR total. |
| `target_bets_per_client` | `target_betcount / target_clients`. |
| `target_stake_per_bet` | `target_stakes / target_betcount`. |
| `target_ggr_margin` | `target_ggr / target_stakes`. |

Targets are not used as features in current scoring snapshots.

## Forecast output fields

The forecast data is generated by `score_snapshot` and exported into reports
and dashboard JSON.

| Field family | Interpretation |
|---|---|
| `predicted_clients`, `predicted_betcount`, `predicted_stakes`, `predicted_ggr` | Point forecasts for the next horizon. |
| `predicted_<metric>_low/high` | Lower/upper prediction band. Non-negative metrics are clipped at zero; GGR may remain signed. |
| `baseline_<metric>` | Baseline/blended reference prediction used for comparison. |
| `confidence_<metric>` | Confidence score derived from WAPE/bin confidence and coverage. |
| `probability_high_client_performer` | Calibrated probability of meeting the client high-performer goal. |
| `probability_high_stakes_performer` | Calibrated probability of meeting the stakes high-performer goal. |
| `probability_high_performance` | Minimum of the client and stakes probabilities when both are present. |
| `predicted_high_*` | Binary flag at the classification threshold; balanced high performer requires both client and stakes flags. |
| `requires_review` | True when client/stakes confidence is below threshold or interval width is too large. |
| `review_reason` | Human-readable reason(s), such as low clients confidence or wide stakes interval. |
| `review_priority` | Numeric severity used to rank review candidates. |
| `recommendation` | Heuristic merchandising label from probability and predicted activity. |
| `external_impact_*` | Recent inferred spike/drop periods from `impact.py`. |
| `Checkpoint`, `Horizon`, `As_Of_Date`, `scored_at` | Scoring lineage and timestamps. |

## Business Report.xlsx

The concise workbook is designed for business stakeholders.

| Sheet | Purpose | Filters/sorting | Business interpretation |
|---|---|---|---|
| `Forecast Capability` | Summarises history days, forecast days, games, average error, metric WAPE, and range coverage. | Grouped by `Obs_Window` and `Horizon`. | Answers “how much history produced what forecast capability?” |
| `Holdout Comparison` | Business-friendly actual vs baseline vs predicted holdout records. | Selected checkpoint/horizon; ordered by business columns. | Use to understand historical forecast performance and high-performer outcomes. |
| `High Performers` | Forecast rows with `predicted_high_performer == 1`. | Filtered to balanced high performers. | Candidate priority set; still review confidence and context. |
| `Forecasting` | Current forecast view with dates, ranges, confidence, review, impact, and performer fields. | Dashboard derives top clients/stakes views from this data. | Operational forward-looking output. |
| `Promo Impact Periods` | Inferred spikes/drops by game and metric. | Grouped by game, metric, and direction. | Context signal, not a confirmed causal promotion record. |

### Holdout Comparison column groups

| Column group | Definition |
|---|---|
| Identity/period: `Game_ID`, `TournamentName`, `SystemName`, `First_Observed_Date` | Game identity and launch lineage. |
| Window: `Observation_Start`, `Observation_End`, `Prediction_Start`, `Prediction_End`, `Obs_Window`, `Horizon` | Historical observation and future evaluation windows. |
| Actual/baseline/prediction: `actual_<metric>`, `baseline_<metric>`, `predicted_<metric>_low`, `predicted_<metric>`, `predicted_<metric>_high` | Actual holdout result, baseline, point forecast, and interval for Clients, Stakes, BetCount, and GGR. |
| Error: `variance_<metric>`, `probability_<metric>` | Signed prediction variance and a bounded closeness score used by the report. |
| Range: `<metric>_actual_in_range`, `<metric>_range_width` | Whether actual fell inside the prediction band and the band width. |
| Tolerance: `off_by_10_pct`, `off_by_20_pct` | Whether any reported metric missed actual by more than 10% or 20%. |
| Goal: `future_performance_score`, `is_high_client_performer`, `is_high_stakes_performer`, `is_balanced_high_performer`, `is_high_performer` | Development-derived goal labels and composite score. |
| Probability: `raw_probability_*`, `probability_*`, `classification_threshold*`, `predicted_high_*` | Raw/calibrated probabilities, thresholds, and binary decisions. |

### Promo Impact Periods columns

| Column | Definition |
|---|---|
| `Game_ID`, `SystemName`, `TournamentName` | Game identity. |
| `Start_Date`, `End_Date` | Contiguous flagged period. |
| `Metric` | One of Clients, BetCount, Stakes, or GGR. |
| `Direction` | `Spike` or `Drop` versus the recent baseline. |
| `Baseline_Value`, `Observed_Value`, `Percent_Change` | Rolling-median reference, observed period value, and percentage movement. |
| `Severity` | `High` at absolute change of at least 100%, otherwise `Medium`. |
| `Reason` | Human-readable inference text. |

## Dashboard JSON datasets

`dashboard.export_dashboard` publishes `dashboard_data.json` and an equivalent
`dashboard_data.js` assignment.

- `summary`: total scored games/systems, predicted totals, confidence rates,
  holdout off-by-10/20 rates, average goal probabilities, and as-of date.
- `systems`: one row per system, aggregated and sorted by predicted stakes in
  Python; the React app also sorts client/stakes views as needed.
- `columns.forecasts`: column keys, labels, display types, and default visibility.
- `forecasts`: latest checkpoint per `Game_ID`, selected by stable sort on
  `Game_ID` and checkpoint then keeping the last row.
- `top_stakes`: top 250 forecast rows by predicted stakes.
- `top_clients`: top 250 forecast rows by predicted clients.
- `review_candidates`: up to 250 `requires_review` rows, sorted by review
  priority then predicted stakes.
- `workbook_sheets`: previews of each report sheet, capped at 250 rows.

## Dashboard filters and sorting

- Search is case-insensitive and scans the available forecast columns.
- System filter matches exact `SystemName`.
- Top Stakes sorts descending `predicted_stakes`.
- Top Clients sorts descending `predicted_clients`.
- Games to Review filters `requires_review` and sorts descending
  `review_priority`, with predicted stakes as the tie-breaker.
- Top Games uses a combined score: `predicted_clients / max_clients +
  predicted_stakes / max_stakes` for the currently filtered rows.
- Tables use stable tie-break sorting and virtualised row rendering for large
  ledgers.

## Example record

```json
{
  "Game_ID": "System A::Tournament 7",
  "Prediction_Start": "2026-10-09",
  "Prediction_End": "2026-10-15",
  "predicted_clients": 1200,
  "predicted_stakes": 85000,
  "predicted_stakes_low": 62000,
  "predicted_stakes_high": 108000,
  "confidence_stakes": 0.73,
  "requires_review": false,
  "predicted_high_performer": 1
}
```

This means the model expects approximately 1,200 clients and ZAR 85,000 in
stakes over the displayed seven-day window, with a range and confidence score;
it does not mean the outcome is guaranteed.
